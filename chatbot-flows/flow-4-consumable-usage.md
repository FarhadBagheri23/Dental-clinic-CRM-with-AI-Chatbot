# فلو ۴ — ثبت مصرف مواد (Consumable Usage)

## Role & Goal

**نقش:** دستیار دندان‌پزشک (Assistant) — کاربر `Staff` با `role = 'دستیار'`

**هدف:** دستیار بلافاصله پس از پایان هر جلسه درمان، مواد مصرف‌شده در آن جلسه را ثبت کند تا موجودی انبار به‌روز بماند و بهای تمام‌شده هر خدمت قابل محاسبه باشد.

**چرا این فلو مهم است:** بدون ثبت دقیق مصرف، `Consumable.stock_quantity` از واقعیت فاصله می‌گیرد و گزارش «بهای تمام‌شده هر خدمت» در داشبورد بی‌معنا می‌شود.

---

## Entities Touched (from ERD)

| موجودیت | نوع دسترسی | فیلدهای درگیر |
|---|---|---|
| `Staff` | خواندن | `staff_id`, `role` — احراز هویت اپراتور |
| `TreatmentSession` | خواندن | `session_id`, `plan_id`, `service_id`, `session_date`, `tooth_number` |
| `Service` | خواندن | `service_id`, `name`, `category` — برای پیشنهاد هوشمند مواد |
| `Patient` | خواندن | `first_name`, `last_name` — نمایش تأییدی |
| `Consumable` | خواندن + **به‌روزرسانی** | `consumable_id`, `name`, `unit`, `stock_quantity`, `min_stock_level` |
| `ConsumableUsage` | **نوشتن** | `consumable_id`, `session_id`, `quantity_used`, `usage_date` |

**رکوردهای ایجادشده:** یک یا چند ردیف در `ConsumableUsage`، به‌همراه کاهش `Consumable.stock_quantity`.

## Validation Rules per Input

| ورودی | قانون اعتبارسنجی | منبع |
|---|---|---|
| `staff_id` | باید در `Staff` موجود باشد **و** `role = 'دستیار'` | `Staff.role` |
| انتخاب جلسه | `session_id` باید در `TreatmentSession` موجود باشد | `TreatmentSession` |
| انتخاب جلسه | جلسه باید متعلق به **امروز** باشد (`DATE(session_date) = CURRENT_DATE`) | قانون کسب‌وکار |
| انتخاب جلسه | جلسه نباید قبلاً کامل ثبت شده باشد (هشدار در صورت وجود) | `ConsumableUsage.session_id` |
| انتخاب ماده | `consumable_id` باید در `Consumable` موجود باشد | `Consumable` |
| انتخاب ماده | ماده نباید در همین جلسه تکراری ثبت شود | منطق کسب‌وکار |
| `quantity_used` | عدد اعشاری با حداکثر ۲ رقم اعشار | `decimal(10,2)` |
| `quantity_used` | **باید بزرگ‌تر از صفر باشد** | قانون کسب‌وکار |
| `quantity_used` | نباید از `Consumable.stock_quantity` بیشتر باشد | یکپارچگی انبار |
| `quantity_used` | سقف منطقی هر قلم در یک جلسه (مثلاً لیدوکائین ≤ ۲۰ میلی‌لیتر) | ایمنی بالینی |
| تأیید نهایی | «بله» / «خیر» / «ویرایش» | — |

### مقادیر تولیدشده توسط سیستم

```
usage_id   = AUTO_INCREMENT
usage_date = TreatmentSession.session_date        ← نه NOW()
```

> ⚠️ `usage_date` باید برابر `session_date` همان جلسه باشد، نه زمان ثبت.
> دستیار ممکن است مصرف جلسه صبح را عصر ثبت کند؛ اگر `NOW()` بگذارید،
> تحلیل «مصرف مواد به تفکیک ساعت/خدمت» در داشبورد نادرست می‌شود.

### به‌روزرسانی موجودی (تراکنشی)

```sql
BEGIN TRANSACTION;

INSERT INTO ConsumableUsage (consumable_id, session_id, quantity_used, usage_date)
VALUES (:cid, :sid, :qty, :session_date);

UPDATE Consumable
   SET stock_quantity = stock_quantity - :qty
 WHERE consumable_id = :cid
   AND stock_quantity >= :qty;          -- جلوگیری از موجودی منفی

COMMIT;
```

> اگر `UPDATE` صفر ردیف تحت تأثیر قرار داد، یعنی موجودی کافی نبوده →
> `ROLLBACK` و بازگشت خطای «موجودی ناکافی» به ربات.

   لیدوکائین ۲٪   ۴۸۰٫۰۰ ← ۴۷۶٫۴۰
   نخ بخیه        ۱۲٫۰۰  ← ۱۰٫۰۰  ⚠️ نیاز به سفارش

**قالب کد ثبت:** `USG-YYYYMMDD-NNNN`

| بخش | معنی | مثال |
|---|---|---|
| `USG` | پیشوند ثابت مصرف (Usage) | `USG` |
| `YYYYMMDD` | تاریخ شمسی جلسه (نه تاریخ ثبت) | `14050503` |
| `NNNN` | `usage_id` اولین قلم این دسته، با صفر پیشرو | `0412` |

> کد ثبت به **کل دسته** اشاره دارد، نه به یک ردیف. دو ردیف `ConsumableUsage`
> ایجاد شد ولی یک کد پیگیری برای دستیار نمایش داده می‌شود.

```

  └─ Capture → {staff_id} → API: GET /staff/{staff_id}
       ├─ role ≠ دستیار → Speak «مجوز ندارید» → [End]
       └─ OK → Set {staff_name}
  └─ API: GET /sessions?date=today&usage_logged=false
       ├─ آرایه خالی → Speak «جلسه‌ای نیست» → [End]
       └─ Dynamic Buttons → {session_id}
  └─ API: GET /sessions/{session_id}  → Set {service_category}, {patient_name}
  └─ API: GET /consumables?category={service_category}   ← پیشنهاد هوشمند
       └─ Dynamic Buttons (+ گزینه «ماده دیگر»)
  ┌─ [ITEM_LOOP] ────────────────────────────────────────────
  │   └─ Buttons/Capture → {consumable_id}
  │        └─ Condition: در {cart} هست؟ → پیام «تکراری» → اصلاح/اضافه
  │   └─ Speak: موجودی فعلی
  │   └─ Capture → {qty} → Code Block: validateQuantity()
  │        ├─ qty <= 0        → خطا → تکرار
  │        ├─ qty > stock     → خطا «موجودی ناکافی» → تکرار
  │        ├─ qty > sane_max  → Buttons تأیید → بله/اصلاح
  │        └─ OK → Push به {cart} (آرایه)
  │   └─ Condition: stock − qty <= min_stock ? Speak هشدار
  │   └─ Buttons: ماده دیگر / تمام
  │        ├─ ماده دیگر → بازگشت به [ITEM_LOOP]
  │        └─ تمام      → خروج از حلقه
  └──────────────────────────────────────────────────────────
  └─ Code Block: ساخت جدول بازبینی از {cart} + محاسبه جمع
  └─ Buttons: بله / خیر / ویرایش
       ├─ ویرایش → Capture ردیف → حذف از {cart} → [ITEM_LOOP]
       ├─ خیر    → پاک‌کردن {cart} → [End]
       └─ بله    → API: POST /consumable-usage  (کل آرایه، یک درخواست)
            ├─ 409 موجودی ناکافی → Speak → [ITEM_LOOP]
            ├─ 500              → Speak «DB-TX-500» → [End]

### نکات پیاده‌سازی

1. **سبد را در ربات نگه دارید، در پایان یک‌جا ارسال کنید.** اقلام را در آرایه `{cart}` جمع کنید و در انتها **یک** `POST` با کل آرایه بفرستید. ثبت قلم‌به‌قلم یعنی اگر دستیار وسط کار قطع شود، جلسه نیمه‌ثبت می‌ماند.
2. **تراکنش در سرور، نه در ربات.** درج `ConsumableUsage` و کاهش `stock_quantity` باید در یک تراکنش پایگاه داده باشند. ربات نمی‌تواند اتمی بودن را تضمین کند.
3. **قید `stock_quantity >= :qty` در همان `UPDATE`.** بررسی موجودی در ربات فقط برای تجربه کاربری است؛ محافظ واقعی قید در `UPDATE` است که از موجودی منفی در شرایط رقابتی جلوگیری می‌کند.
4. **`usage_date` را از جلسه بگیرید، نه از ساعت سیستم** (بند بالا در بخش اعتبارسنجی).
5. **پیشنهاد هوشمند مواد** را از `Service.category` بسازید: جراحی ← لیدوکائین/نخ بخیه/گاز؛ درمانی ← کامپوزیت/باندینگ/ماتریس؛ تشخیصی ← فیلم رادیوگرافی. این تعداد ضربه کلید دستیار را چند برابر کم می‌کند.
6. **اقلام همیشگی را پیش‌فرض کنید.** دستکش و ماسک در هر جلسه مصرف می‌شوند؛ می‌توانید آن‌ها را از پیش در `{cart}` بگذارید تا دستیار فقط تأیید کند.
7. **هشدار موجودی، خطا نیست.** رسیدن به `min_stock_level` باید پیام هشدار بدهد اما مسیر را متوقف نکند. فقط «موجودی ناکافی» مسدودکننده است.
8. **حلقه اقلام را با آرایه بسازید،** نه با کپی بلوک. Voiceflow آرایه‌ها را در متغیر پشتیبانی می‌کند؛ از `{cart}` و یک بلوک `Set` با `push` استفاده کنید.
9. **ارقام اعشاری فارسی.** ورودی ممکن است `۳٫۶` (ممیز فارسی `٫`) باشد؛ در Code Block آن را به `3.6` نرمال کنید پیش از `parseFloat`.
10. **اعلان کمبود انبار.** وقتی موجودی زیر حد سفارش رفت، علاوه بر پیام به دستیار، یک رویداد به حسابدار/انبار بفرستید (وبهوک یا ردیف در جدول اعلان‌ها).
